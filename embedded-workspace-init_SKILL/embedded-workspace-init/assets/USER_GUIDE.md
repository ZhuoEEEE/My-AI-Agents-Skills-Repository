# 嵌入式 Agent 工作区使用手册

## 60 秒开始

1. 在 Codex 中只打开本目录，并选择 `Local` 环境。不要为本目录创建 Codex worktree，也不要把 `sources/` 或 `work/` 下的副本单独保存为项目。
2. 直接描述任务，例如“构建 motor-controller 的 debug 配置”或“继续电机堵转保护任务”。Agent 会在独立 workstream 中修改和验证。
3. 用户原工程默认只读。需要写回时明确说“把当前 workstream 的修改同步回我的工程”；发布前先保存 IDE 和编辑器中的文件。

## 三种工程位置

- **用户权威工程**：您继续用原 IDE 维护的原始工程，位于本工作区之外。除明确发布或单独授权用户 Git 操作外，Agent 不写这里。
- **集成副本**：`sources/<source-id>/integration/`，用于导入用户已保存内容、保存同步基线和汇总，不是日常编辑目录。
- **Workstream**：`work/<workstream-id>/sources/<source-id>/`，每个逻辑任务一份独立 Git worktree；正常修改、生成、构建和测试都在这里进行。

多个 MCU 可以属于同一源组，也可以分属多个源组。分散但共享相对路径或生成配置的目录会用多个可逆映射保持原拓扑。多个对话默认使用不同 workstream；明确说“继续 <workstream-id>”才复用已有任务。写入范围重叠时 Agent 会先报告冲突。

## 编辑器内 Agent 插件

您可以继续在 VS Code、IDE 或其他可安装插件的编辑器中，用编辑器内的 Agent 插件直接修改用户权威工程。插件已保存到磁盘的修改就是用户权威工程的当前内容；这类插件不属于本 Skill 管理的 Agent 工作区，因此本 Skill 不会为它建立 workstream、副本、管理目录或额外 Git。

需要把这些修改带入 Agent 工作区时，请先保存文件，再请求“把我的工程最新修改导入 Agent 工作区”。未保存的编辑器缓冲区对本 Skill 不可见。如果 Agent 工作区同时有未发布修改，仍会按现有三方比较和冲突处理流程执行，不会静默覆盖。

用户权威工程可以继续由 VS Code、IDE 及其插件维护，但不能直接作为 Codex 日常项目入口；Codex 日常任务仍应从纯净 Agent 工作区根目录以 `Local` 环境启动。

## 自动事项与需确认事项

Agent 会轻量检查已登记源、导入无冲突的已保存修改、补充明确的新目标、维护私有基线并在可用时执行已验证构建。它不会扫描整台电脑、安装或升级工具链、修复初始化时的业务代码、转换工程系统、自动生成源码或操作板卡。

以下事项需要明确意图：向用户工程发布、初始化或提交用户 Git、提升参考工程为正式源码、改变映射/布局/规则、创建阶段归档，以及烧录或调试。OTP、eFuse、永久读保护、Option Bytes、Bootloader 区和含重要数据的全片擦除每次都必须确认。

“只读”“只检查”或“不更新状态”具有最高优先级：不会创建配置、目录、日志、备份、Git 对象、构建输出或事实更新。

## 三套 Git

Agent 工作区内部由 Agent 管理。如果您直接修改了内部文件，Agent 会先将这些修改保存并验证到 `preserved-user/*` 分支，再恢复对应文件到修改前的 Agent 检查点，继续当前任务，最后告知分支、提交和文件范围。此流程不需要反复确认，不会自动合并您的内部改动。已暂存内容和磁盘内容分别保留，新增、删除和二进制文件也适用。

该规则不适用于外部用户权威工程；外部修改仍正常导入。Git 忽略的本机配置、运行状态以及含密钥的文件不能强行提交，须通过对应恢复机制保存和核验；同一文件混有 Agent 和用户改动时先分离，不能整份回退。只读任务仍然零写入。

- **Agent 管理 Git**：本目录根 `.git`，只管理规则、说明、可移植配置、schema、模板、项目知识和任务元数据。根 `git status` 不代表源码状态。
- **源组私有 Git**：每个 `sources/<source-id>/integration/` 一套，自动保存用户同步基线、任务分支和内部检查点，不推送回用户仓库。
- **用户工程 Git**：可选，由您决定是否初始化和何时提交。发布默认只改工作树，不自动提交或推送。

一个目标可有多个稳定 `build-id`，如 `debug`、`release`。请在有歧义时同时指定 target 和 build-id。源码状态需要分别查看当前 workstream 中各源组的 Git，不能只看根 Git。

## 导入、发布与恢复

“把我的工程最新修改导入 Agent 工作区”表示用户工程到副本；“把当前 workstream 的修改同步回我的工程”表示副本到用户工程。只说“同步”且方向不清时，Agent 会询问。

用户同步基线保存最后一次双方一致且可取回的内容；构建基线只保存某 target/build-id 最近一次实际构建成功的提交。没有成功构建过也能进行三方同步，两种基线不会互相替代。

发布会冻结任务提交和固定依赖，重新扫描用户工程，逐文件三方比较，先完成全部预检和恢复快照，再按哈希前置条件原子写入。它不会用目录镜像覆盖或隐式删除。冲突会在写入前停止；应用失败会在能证明现场未被外部修改时整体回滚。

文件正确但用户工程构建失败时，现场和快照会保留，等待您选择保留或回滚。自动回滚无法证明安全时进入 `recovery_required`，新的导入和发布暂停，避免覆盖后续修改。构建产生未登记工程文件时同样暂停基线推进，先确认其属于输出、生成文件还是异常副作用。

请记住：Agent 只能读取已保存到磁盘的内容，无法保护 IDE 中未保存的缓冲区。这里提供的是工作副本、哈希、Git 和快照形成的软隔离，不是操作系统级绝对隔离。

## 参考工程与项目知识

`reference-projects/<reference-id>/project/` 是保持原结构的只读快照，不会自动成为构建目标或发布内容。需要试改或构建时，使用 `work/<workstream-id>/reference-copies/<reference-id>/project/`；该副本有独立临时私有 Git，来源和清理条件记录在外层 README 中。任务完成且成果已保留后才可清理。

跨任务长期事实位于 `project-docs/`：`PRODUCT.md` 记录产品目标，`SOLUTION.md` 记录当前有效方案，`ROADMAP.md` 记录阶段和退出条件，`decisions/` 保存可追溯决策，`versions/` 保存版本边界。初始化只创建职责说明和模板，不创建空正文；workstream 中的候选结论经您确认后才会提升为项目事实。

## 初始化、迁移与规则升级

从已有用户工程开始时，选择一个与用户工程互不包含的外部空目录作为 Agent 工作区。Skill 会先展示真实路径、源组映射、过滤项、三套 Git、验证和回滚方案；需要计划确认时，确认前零写入。

非空旧 Agent 工作区不会原地重组。确认后在新的空路径创建工作区，旧目录保持原样并作为按需只读的历史参考，不自动扫描、构建、同步或发布，也不能从旧路径启动日常 Codex。需要修改旧内容时先复制到当前 workstream 的参考副本。

工作区规则、结构、映射或 schema 升级采用两阶段流程：先只读展示完整计划并停止；明确确认且复查无变化后才备份、归档旧规则、应用、验证和记录。失败时回滚管理文件，不会顺带写用户业务源码。

固定目录骨架及职责 README 在初始化时创建；具体项目文档、参考实例、workstream、证据、日志、恢复快照和迁移记录只在真实操作发生时生成。活跃工作区只有根 `AGENTS.md` 生效，归档旧规则仅供审计。

旧管理对话目录不是新工作区的必迁内容。明确不保留旧规则时，它们仅留在旧目录，不复制归档；也可不登记旧目录为历史访问路径。新 `workspace-management/` 仍是配置和工具的固定运行目录。

## 常用表达

```text
把我的工程最新修改导入 Agent 工作区。
重新扫描并登记新增 MCU 工程。
构建 motor-controller 的 debug 配置。
查看当前正在进行的任务。
继续 20260910-motor-stall-a13f。
把当前 workstream 的修改同步回我的工程。
为用户工程启用 Git。
恢复发布前的工程副本。
将 <path-or-url> 添加为参考工程。
参考 <reference-id> 分析驱动，但不要修改参考工程。
把 <reference-id> 复制到当前任务中供试改和构建。
将 <reference-id> 提升为正式开发工程，但先不建立用户发布映射。
参考迁移前的旧工作区分析历史方案，但不要在那里修改或构建。
更新已有工作区约束，先只展示迁移计划。
```

这些是自然语言示例，不是固定口令。
