# embedded-workspace-init 使用说明

## 1. Skill 用途

`embedded-workspace-init` 用于在 Windows 本地环境中初始化、迁移或受控更新嵌入式/MCU 产品的 Agent 工作区。

创建任务记录与创建工程副本分开：建立 workstream 不检出工程，修改、生成或构建前才挂载所需的完整工程及显式共享依赖，正式完成时检查并释放合格副本。

它把用户日常维护的原始 IDE 工程视为“用户权威工程”，在外部独立目录建立 Agent 工作区。Agent 默认只读用户权威工程，在受管副本中进行开发、构建和验证；只有用户明确要求发布时，才通过受控流程把指定任务的修改写回用户工程。

该 Skill 主要提供以下能力：

- 从一个或多个现有 MCU 工程建立独立 Agent 工作区。
- 保留用户原有目录结构、IDE 工程和开发习惯。
- 支持单 MCU、多 MCU、多个分散源码目录和多个并行任务。
- 保留源组共同拓扑，按完整工程及共享依赖管理任务副本，支持同任务追加工程和逐工程释放。
- 分离 Agent 管理 Git、源组私有 Git 和用户 Git。
- 对用户工程与 Agent 修改进行三方比较并处理冲突。
- 将用户直接修改的内部受管文件保存到独立分支，验证后恢复 Agent 检查点。
- 为发布失败提供恢复快照、验证和回滚机制。
- 将旧 Agent 工作区迁移到新的纯净目录，并保留旧目录不变。
- 在已有工作区中刷新项目事实，或对规则、结构和 schema 执行受控升级。
- 导入只读参考工程，或将参考工程提升为正式开发源。

## 2. 何时使用

适合显式调用本 Skill 的请求包括：

- 首次创建嵌入式 Agent 工作区。
- 从已有用户工程创建外部 Agent 工作区。
- 迁移非空旧 Agent 工作区。
- 重新扫描并登记新增 MCU 工程或构建目标。
- 向已有工作区增加新的用户源或 Agent 自建源。
- 调整用户源到 Agent 副本的目录映射。
- 导入、复制或提升参考工程。
- 更新工作区规则、布局、映射、policy 或 schema。
- 只读检查工作区是否满足安全约束。

以下请求通常不应调用本 Skill：

- 普通固件功能开发。
- 一般缺陷修复或代码审查。
- 已初始化工作区中的日常构建和测试。
- 普通 workstream 的继续开发。
- 单纯把当前任务发布回用户工程。

初始化完成后的日常工作由 Skill 生成的根 `AGENTS.md` 和受管工具负责，不需要每次重新调用初始化 Skill。

## 3. 调用方式

该 Skill 只允许显式调用。请求中必须写出：

```text
$embedded-workspace-init
```

建议同时说明：

- Agent 工作区目标路径。
- 用户权威工程路径。
- 是首次初始化、迁移、刷新还是升级。
- 是否只允许检查。
- 是否存在多个分散工程目录。
- 是否存在旧 Agent 工作区。
- 是否需要导入参考工程。

## 4. 常用调用示例

### 4.1 从现有工程初始化

```text
$embedded-workspace-init
使用 D:\Firmware\motor-controller 作为用户权威工程，
在 D:\AgentWorkspaces\motor-controller 建立独立 Agent 工作区。
保留现有 IDE 工程和目录结构；需要确认时先给出完整计划。
```

### 4.2 使用多个用户工程路径

```text
$embedded-workspace-init
使用以下路径初始化当前产品的 Agent 工作区：
- D:\Firmware\main-controller
- D:\Firmware\sensor-controller
- D:\Firmware\shared
请先判断合理的源组和目录映射，不要移动或重组原工程。
```

如果多个分散目录必须保持共同相对关系，应在请求中说明。Skill 使用多个可逆映射保存必要拓扑。

### 4.3 创建 Agent 自建工程工作区

```text
$embedded-workspace-init
在 D:\AgentWorkspaces\new-device 创建新的嵌入式 Agent 工作区。
目前没有用户权威工程，源码由 Agent 后续创建。
```

这种源不会虚构用户工程路径，也没有导入或发布方向。

### 4.4 只读检查

```text
$embedded-workspace-init
只读检查 D:\AgentWorkspaces\motor-controller 的工作区状态、
路径隔离、Git 边界和目标登记情况。
不要创建或修改文件、目录、日志、Git 对象或构建输出。
```

“只读”“只检查”“不要更新状态”等表达表示绝对零写入。

### 4.5 迁移旧工作区

```text
$embedded-workspace-init
检查旧工作区 D:\OldAgent\motor，
并为新的空目录 D:\AgentWorkspaces\motor-v2 制定迁移计划。
确认前不要写入，旧目录必须保持原样。
```

第一次调用只生成迁移计划。用户明确批准完整且未变化的计划后，Skill 才会应用迁移。

默认会归档旧规则并登记旧工作区历史路径。如果明确不保留旧管理机制，可以在请求中说明：

```text
旧规则只留在旧目录，不复制规则正文或归档清单；
不登记旧工作区为历史访问路径；
将不需要迁入的旧管理目录明确分类为 preserve-only，原文件保持不动。
```

旧规则处置、旧路径登记和普通资料复制分别配置，并纳入迁移计划摘要。新工作区创建自身所需的管理目录和工具。

### 4.6 刷新已有工作区

```text
$embedded-workspace-init
重新扫描当前工作区，登记新增 MCU 工程，保留已有确认信息。
只执行事实刷新；如果涉及规则、结构、映射或 schema 变化，先给出升级计划。
```

### 4.7 添加新的用户源

```text
$embedded-workspace-init
将 D:\Firmware\display-controller 作为新的用户权威源加入当前工作区。
先展示 source-id、目录映射、过滤项和 Git 边界。
```

### 4.8 导入参考工程

```text
$embedded-workspace-init
将 D:\References\vendor-demo 导入为参考工程，
reference-id 使用 vendor-demo，仅供查阅，不作为开发或发布目标。
```

从 Git 导入时，应提供固定 commit 或 tag，而不是只提供会移动的分支名：

```text
$embedded-workspace-init
将 <repository-url> 的 <commit-or-tag> 导入为参考工程，
记录用途、适用目标、许可证和已知差异。
```

### 4.9 更新规则或结构

```text
$embedded-workspace-init
更新当前工作区的管理约束。
先只读展示当前与目标版本、文件操作、Git 影响、验证和回滚计划；
确认前不要写入。
```

## 5. 使用前提

当前 Skill 面向以下环境：

- Windows 本地主机。
- 本地文件系统路径。
- PowerShell 7。
- Git。
- Codex `Local` 环境。

调用前应保存 IDE 和编辑器中的文件。Skill 只能处理已经写入磁盘的内容，无法读取或保护未保存缓冲区。

## 6. 路径要求

Agent 工作区与用户权威工程必须位于两个互不包含的真实目录中。

以下布局会被拒绝：

```text
用户工程\agent-workspace\...
```

```text
Agent工作区\user-project\...
```

以下情况同样会阻止初始化：

- 通过符号链接或 junction 形成间接包含。
- 用户工程直接充当 Agent 集成副本。
- 路径不存在、不可读或真实路径无法确定。
- 候选根属于外层 Codex worktree。
- 同一用户权威源已知属于另一个活动工作区。

新工作区目标目录应为空。非空候选目录不会被直接覆盖，而是进入迁移规划流程。

## 7. Skill 如何选择操作路线

### 7.1 空的新目录

当目标目录为空、路径安全且源映射明确时，显式初始化请求可以直接建立工作区。

### 7.2 已激活工作区

Skill 会保留稳定 ID 和用户确认字段，只执行请求范围内的幂等刷新。

如果检测到规则、布局、固定结构、映射或 schema 变化，Skill 不会把它当作普通刷新，而会切换到受控升级计划。

### 7.3 正在初始化的工作区

只允许：

- 检查状态。
- 继续同一个已批准初始化。
- 放弃未完成候选。

在工作区变为 `active` 前，不能进行普通开发、导入或发布。

### 7.4 非空未管理目录或旧工作区

Skill 先只读盘点并给出完整迁移计划。确认前零写入。

迁移必须使用新的空目录；旧目录不会被移动、重命名、交换或删除。

### 7.5 工作区位于用户工程内

Skill 不会在该位置创建任何内容，只会报告冲突并要求用户选择外部空目录。

## 8. 初始化会创建什么

初始化结果是一个独立 Agent 工作区，主要包含：

- 根 `AGENTS.md`：后续 Agent 的工作规则。
- 根 `README.md`：工作区入口和目录概览。
- 根 `USER_GUIDE.md`：初始化后的用户使用手册。
- 可移植配置和本机配置。
- JSON schema。
- 受管 PowerShell 工具。
- 用户源的集成副本和源组私有 Git。
- 项目任务、参考工程、项目知识、证据和恢复数据的分类位置。

项目知识正文、参考工程实例、workstream、构建证据和恢复快照在对应操作发生时创建。

### 8.1 源组、完整工程与构建入口

源组负责共同源码拓扑、私有 Git、映射和同步基线。例如，一个产品的 `motor-product` 源组可以同时管理 STM32 工程、其他芯片工程和共享协议。完整工程及显式共享依赖是工程副本的挂载和释放单位。

| 层次 | 示例 | 用途 |
| --- | --- | --- |
| 产品／项目 | 电机控制产品 | 整体产品边界 |
| 源组 | `motor-product` | 共同源码拓扑、私有 Git、映射和同步基线 |
| 完整工程 | `firmware/motor-controller/` | 工程源码、驱动、生成配置和 IDE 配置的完整边界 |
| 构建入口 | `firmware/motor-controller/MDK-ARM/` | 某个 IDE 或构建配置入口 |

`sources/` 下的一级目录是源组 ID。完整 STM32 工程通常包括 `Core`、`Drivers`、`.ioc` 和 `MDK-ARM` 等内容，`MDK-ARM/` 是工程内的构建入口。CMSIS 内部示例和库内入口按所属工程识别。

工程使用稳定 `project_id` 登记完整根目录 `root` 和显式共享依赖 `shared_paths`；共享依赖可以是目录或单个文件，保持原来的源组内相对位置。构建目标通过 `project_id` 关联所属工程。边界或必要依赖不明确时，先明确登记，不自动扩大为整个源组。

### 8.2 工程副本何时出现

创建 workstream 时建立任务清单、说明、工具和产物目录，不立即创建工程工作树。没有源码范围的文档任务可以使用空 scope 和 refs；用户明确要求只读时，连任务记录也不创建。

- 讨论方案、查资料、阅读源码或整理工作区文档时，不创建工程副本；必要的源码检查可从集成副本读取。
- 首次修改源码、`.ioc`、IDE 工程配置前，先挂载当前任务所需的完整工程及登记依赖。
- CubeMX 生成或编译等会写工程目录的操作，同样先挂载。
- 同一任务后来需要另一个工程时，追加该工程，不重建任务，也不覆盖已有工程的修改。
- 已挂载工程继续使用当前副本。多个工程的实际检出范围是工程根和共享依赖的并集。

首次挂载采用 `git worktree add --no-checkout` 加精确稀疏检出，直接落地所需路径。`sources/<source-id>/integration/` 保存完整的受管集成副本和源组私有 Git；`work/<workstream-id>/sources/<source-id>/` 保存按需挂载的任务工程副本。不同任务使用独立工作树，各自拥有工程和共享依赖的物理文件。

### 8.3 完成、释放和恢复

任务正式标记为 `completed` 且没有未解决修改时，受管工具自动逐工程检查并尝试释放合格副本。一轮回复结束不等于任务正式完成；暂停、阻塞、未解决修改、待处理发布或恢复事务，以及已登记命令仍引用工程实际目录等情况，会保留受影响副本。

也可以直接提出：

```text
释放 <workstream-id> 中 <source-id> 的 <project-id> 工程副本，保留任务记录和成果。
```

释放遵守以下边界：

- 指定工程路径有待提交修改时保留该工程。
- 工程内需要移出的未跟踪文件、被忽略文件和已确认且仍有效的构建输出，先转存到该任务的 `artifacts/project-copy-preserved/` 并核对哈希，再移除原位置。
- 只收缩该任务的检出范围；其他工程及它们仍需的共享依赖继续保留。
- 最后一个工程及依赖释放后，正常注销物理工作树，继续保留任务记录、报告、工程外其他产物，以及源组私有 Git 中的任务分支和提交。
- 之后可按保留的任务提交重新挂载，不静默改用最新 integration 状态。
- Git 不能安全收缩时停止或回滚，不强制删除；回滚无法证明完整时记录工程副本 `recovery-required` 并阻止该源组继续相关操作。

工程产物转存目录由管理 Git 忽略。已完成任务的副本回收使用相同工具和逐工程检查流程。

### 8.4 工程副本管理入口

日常受管入口位于已初始化工作区的 `workspace-management/tools/`：

- `set-source-project.ps1`：通过 `-SourceId`、`-ProjectId`、`-ProjectRoot`、`-SharedPath` 和 `-TargetId` 登记或更新工程边界、共享依赖和目标关联。
- `manage-project-copy.ps1`：通过 `-WorkstreamId`、`-SourceId`、`-ProjectId` 和 `-Action Mount|Release` 挂载或释放指定工程。

两者默认只输出零写入计划；实际应用使用相同参数加 `-Apply -ExpectedPlanDigest <plan_digest>`。计划后内容发生变化必须重新规划；重复挂载、释放或登记保持幂等，不产生空提交。增加新源组前先更新任务 scope；物理挂载范围不替代任务的读写授权范围。

## 9. 用户工程会不会被修改

“用户权威工程默认只读”只约束本 Skill 及其管理的 Codex Agent。用户本人、原有 IDE 或编辑器内 Agent 插件仍可以在本 Skill 之外直接维护用户权威工程。

Skill 不会因为初始化而在用户工程中创建：

- `AGENTS.md`
- `README.md`
- `USER_GUIDE.md`
- `.gitignore`
- `.git`
- Agent 管理目录
- Agent 工作副本

对本 Skill 管理的 Agent，用户工程写入仍只允许通过以下入口：

- 用户明确要求将某个冻结 workstream 发布回用户工程。
- 用户明确授权启用或操作用户 Git。

### 9.1 编辑器内 Agent 插件

- 编辑器内 Agent 插件可以直接修改用户权威工程。
- 插件保存到磁盘的修改属于用户权威工程当前内容。
- 插件不属于本 Skill 管理的 Agent 工作区；Skill 不为它创建 workstream、副本、管理目录或额外 Git。
- 导入前必须保存文件；未保存的编辑器缓冲区对 Skill 不可见。
- 如果 Agent 工作区同时存在未发布修改，继续执行三方比较和冲突处理，不静默覆盖。
- 用户工程可以继续由 IDE 及其插件维护，但不能作为 Codex 日常项目入口；Codex 日常任务仍从纯净 Agent 工作区根目录以 `Local` 环境启动。

## 10. 初始化不会做什么

Skill 不会在初始化阶段：

- 修改业务源码以修复错误。
- 自动解决编译失败。
- 安装或升级 IDE、工具链、SDK、Pack 或许可证。
- 转换构建系统。
- 清理用户工程缓存。
- 重新生成源码。
- 烧录、擦除、复位或调试板卡。
- 改变系统权限。
- 自动提交或推送用户 Git。
- 扫描整台电脑寻找工程。

工程当前不能编译不一定意味着工作区初始化失败。布局验证和构建验证是两个不同结果。

## 11. 三套 Git 的区别

Skill 建立或识别三种彼此独立的 Git 域：

### 11.1 Agent 管理 Git

位于 Agent 工作区根目录，只管理规则、配置、schema、工具、模板、项目知识和任务元数据。

### 11.2 源组私有 Git

每个源组独立使用，用于保存用户同步基线、任务分支和工作副本。它不向用户仓库推送。

### 11.3 用户 Git

用户工程自己的 Git，可选且必须单独授权。初始化和普通发布不会自动提交或推送用户 Git。

因此，工作区根目录的 `git status` 不能代表源码修改状态。

### 11.4 用户直接修改内部文件

Agent 工作区内部由 Agent 管理。如果用户直接修改了内部受管文件，Agent 会先区分修改归属并保存自身改动，然后通过 `preserve-user-changes.ps1` 处理明确选定的用户修改：

1. 生成只读计划，记录文件范围、当前 Agent HEAD、暂存区状态和磁盘内容。
2. 按有效摘要执行，将选定文件的暂存区内容和磁盘内容分别保存为提交，保留在 `preserved-user/*` 分支上。
3. 验证保存成功及现场未变化后，仅将选定文件和暂存区条目恢复到原 Agent 检查点。
4. 继续任务，并告知保存分支、两个提交、文件范围和恢复结果。

保存支持新增、删除、二进制文件和已暂存修改。即使磁盘内容已经改回 HEAD、暂存区仍有修改，也会保存暂存区内容。保存分支保留用户内容，选定文件恢复到原检查点，Agent HEAD 和其他路径保持不变。

该流程按明确的文件范围和修改归属执行。同一文件混有 Agent 和用户修改时先分离；归属明确且保存核验通过后恢复。只读任务零写入。

外部用户权威工程中的用户本人和编辑器内 Agent 插件修改，通过导入、三方比较和冲突处理进入工作区。Git 忽略的本机配置和运行状态通过对应恢复机制及已验证快照保留；保存分支按敏感文件过滤规则处理内容。

## 12. 导入和发布方向

Skill 使用三个明确方向：

- `inspect`：只读比较。
- `import`：用户权威工程到 Agent 副本。
- `publish`：Agent workstream 到用户权威工程。

用户本人或编辑器内 Agent 插件保存到磁盘的修改，都通过相同的受管导入、三方比较和冲突处理流程进入 Agent 工作区。未保存的编辑器缓冲区对 Skill 不可见。

导入保留当前任务已有的稀疏检出边界。某工程尚未挂载或已经释放，不表示其文件被删除；任务和依赖差异按源组私有 Git 中的提交比较。上游工程副本释放后，固定依赖仍可从保留的提交读取。

常用自然语言示例：

```text
把我的工程最新修改导入 Agent 工作区。
```

```text
把当前 workstream 的修改同步回我的工程。
```

如果只说“同步”且无法判断方向，Agent 会询问。

发布前会：

1. 确认当前 workstream，并挂载待发布工程及固定依赖闭包所需路径。
2. 提醒保存 IDE 和编辑器文件。
3. 冻结任务提交及固定依赖。
4. 重新扫描用户工程。
5. 逐文件进行三方比较。
6. 完成全部预检和恢复快照。
7. 生成绑定内容的发布摘要。
8. 只有摘要仍有效时才逐文件写入。

Skill 不会使用目录镜像覆盖或隐式删除用户工程。

只读比较或发布预检不会隐式创建工程副本。缺少待发布工程或依赖路径时，预检会要求先恢复挂载，再进入冻结、三方比较和发布流程。

## 13. 冲突与恢复

以下情况会在写入用户工程前停止：

- 用户和 Agent 修改了同一位置。
- 文件在计划后发生变化。
- 目录映射已经变化。
- 扫描不完整。
- 基线或依赖提交不可取回。
- 修改超出 workstream 范围。

发布会为受影响文件建立恢复快照并记录哈希。修改使用同目录临时文件和原子替换；删除先进入恢复区。

应用失败时，只有在能证明现场没有被外部修改时才自动回滚。无法安全证明时，工作区进入 `recovery_required`，新的导入和发布会暂停，避免覆盖后续修改。

文件发布正确但用户工程构建失败时，Skill 会保留现场、快照和证据，等待用户决定保留或回滚。保留失败构建的文件不会被记录为构建成功。

## 14. 敏感文件与复杂 Git

导入会保留法律和工程必需内容，例如许可证、版权声明、启动代码、链接脚本和必要二进制依赖。

Keil 工程导入过滤 IDE 用户状态和已知可重建输出，工程必需的 `.sct` 链接脚本作为构建输入保留。

以下内容不会被自动纳管：

- `.git` 元数据。
- IDE 本机工作区状态。
- 已确认可重建的缓存和输出。
- 私钥、令牌、生产签名材料和许可证激活秘密。
- 设备数据转储等高风险内容。

二进制文件按用途和内容分类，高熵作为辅助信息。用途不明的法律文件或许可证内容进入待确认清单。

发现 submodule、嵌套 Git、已有 linked worktree 或 Git LFS 时，Skill 会暂停受影响源组，不会自动展平或改写历史。

## 15. 参考工程

通过本 Skill 导入的参考工程是不可变、经过过滤并带有来源清单的快照。

参考工程：

- 不自动成为源码源组。
- 不自动成为构建目标。
- 不参与用户工程发布。
- 不应直接修改。

需要试改或构建时，应为当前 workstream 创建独立参考副本。明确要求提升时，参考工程可成为正式开发源，但不会自动获得用户发布路径。

## 16. 规则和结构升级

工作区规则、结构、映射、policy 或 schema 升级采用严格的两阶段流程：

1. 只读审计并展示完整计划。
2. 用户明确批准未变化的完整计划后执行。

计划应说明：

- 当前和目标版本。
- 将创建、修改、归档或保留的内容。
- 对源组、Git、workstream、构建和同步的影响。
- 执行前快照和检查点。
- 应用后验证。
- 失败回滚方式。

部分批准不会触发部分实施。Skill 会先生成新的完整计划并再次等待确认。

### 16.1 从版本 1 升级到版本 2

版本 1 到 2 迁移将工作区的 `workspace_schema`、`policy_version`，以及 targets 和 workstream 的 schema 设置为 2，登记完整工程和逐工程挂载状态。source、target、build、mapping ID、映射版本和同步基线保持对应关系，其他状态文件使用各自 schema 版本。

已有完整任务工作树记为 `legacy-full`，元数据迁移保留其物理内容，包括暂停任务的未提交修改。工程副本回收通过工程副本管理工具单独执行逐工程检查和释放。

已有工作区通过具体升级计划、确认、快照、应用和验证流程完成迁移。

## 17. 常见停止条件

Skill 遇到以下情况会停止，而不是自行猜测：

- 路径不存在、不可读或不是本地路径。
- Agent 工作区与用户源互相包含。
- 源组或目录映射有歧义。
- 完整工程根目录或必要共享依赖不明确，或构建、发布所需工程尚未挂载。
- 文件扫描不完整或复制过程中源发生变化。
- 发现复杂 Git 拓扑。
- 工作区状态不允许当前操作。
- schema 或 JSON 校验失败。
- 共享状态锁超时。
- 迁移、升级或发布摘要已经过期。
- 发布文件在写入前发生漂移。
- 自动回滚无法证明安全。
- 工程副本处于 `recovery-required`，或命令／响应脚本仍指向其他任务的工程目录。

停止回复应明确说明阻断原因、已经完成的只读检查、尚未发生的写入以及下一步需要的决定。

## 18. 初始化完成后

初始化成功后，应从新 Agent 工作区真实根目录打开 Codex，并使用 `Local` 环境。

用户权威工程可以继续在原 IDE 或编辑器内 Agent 插件中打开和维护，但不能作为本工作流的 Codex 日常项目入口。

不要把以下位置单独作为 Codex 项目：

- 用户权威工程。
- 集成副本。
- workstream 源码副本。
- 参考工程正文。

后续普通开发直接描述任务即可。只有再次初始化、迁移、刷新管理事实、导入参考工程或升级工作区约束时，才需要重新调用 `$embedded-workspace-init`。

需要构建或生成时，先挂载当前任务的工程和依赖，并确认命令及响应脚本指向当前任务。不要借用暂停任务的工程路径执行操作。正式完成后由受管工具检查释放；保留的任务记录和成果仍可用于后续交接或恢复。
